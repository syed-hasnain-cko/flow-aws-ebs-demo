3. Standalone 3DS — Hosted Session

Create a session, send the cardholder to Checkout.com's hosted authentication page, read the result, then authorize the payment with the session id — or with the raw 3DS data (as you would with a third-party PSP). Needs sessions:browser scope on your OAuth client.
Step 1 · Request a session — POST /sessions
Frictionless & exemptions — redirectless (HTTP 201) flow, completion type and presets
Normally POST /sessions returns 202 pending and the cardholder is redirected so Checkout.com can collect their browser data. If you already hold that data and send it as channel_data, a frictionless result comes back immediately as 201 approved — no redirect, with the eci and cryptogram. A card that needs a challenge still returns 201 (challenged) and, for hosted sessions, a redirect link for the challenge only.

3. Account Updater & Real-Time Account Updater

    
⚠️
Requires enablement on the merchant account (Standalone Account Updater, RTAU: Mastercard Store & Update / Update & Retry, Visa Account Updater). Without it you will see 401/403/422 — the UI shows exactly what came back. Public docs list no test cards; the simulator cases from CKO's internal “Account Updater Sandbox Simulator Test Cases” document are built in below (section C), each with the card, amount and expected outcome. The standalone endpoint answered for Mastercard and returned merchant_not_onboarded for Visa on the account it was verified on.


    
A · Standalone Account Updater — POST /account-updater/cards (Visa, Mastercard, Amex)

    
Uses the card source above: a saved instrument sends source_options.instrument.id; a raw card sends source_options.card. Amex updates run in batch — request at least 24h before use.

    
Request preview

    

    


    
B · Real-Time Account Updater — triggers inside POST /payments

    
RTAU fires automatically on eligible payments: a MIT or card-on-file CIT, using a stored instrument or full card details (not network tokens), amount > 0. The outcome is in the payment's source.account_update_status, and the card_updated webhook carries the original and replacement card.

C · RTAU simulator test cases — from “CKO Account Updater Sandbox Simulator Test Cases”

    
Each case creates a fresh Source ID from the case's test card, sends the documented payment, then scores the real response against the document's expectation (response code, account_update_status, failure code, replacement card, webhook). “Sandbox” shows what was actually observed when these cases were run — the document colour-codes working / non-working cases and that key is not in its text.
