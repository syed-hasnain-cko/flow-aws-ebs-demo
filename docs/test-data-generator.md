# Test Data Generator tab (2026-11-12)

Nav: Tools → 🧪 **Test Data** · `tabs/testdata.html`, `modules/testdata.js`, backend `src/testdata/testdata-routes.js` (mounted at `/testdata`).
Creates realistic **sandbox** transactions in an account with nobody at the keyboard, so there is no 3D Secure: customer payments are sent with `3ds.enabled:false`, merchant-initiated payments are backend-only. **Sandbox only** — a live key/URL is refused server-side.

## What the user does
1. **Account** — "Default account" (Settings account, else the server's) or saved **merchants**: name, optional prefix, sandbox public key (needed for Pay to card), sandbox secret key → sealed by `POST /testdata/seal` (AES-256-GCM, own key label + AAD, so a token from here is useless in Settings / Wallet Onboarding); the browser keeps only the opaque token (`cko-testdata-profiles`, marked sensitive → never exported). Per account: **several processing channels** (payments are spread round-robin), the **currency account id** (payouts), and which **card brands** to use. All 8 brands with documented approval test cards are offered (Visa, Mastercard, Amex ticked by default; Cartes Bancaires, JCB, Discover, Diners, UnionPay opt-in) with a disclaimer that a brand must be **enabled in the sandbox** first. "Check which cards this account accepts" = one tiny payment per brand, then ticks only those that were approved.
2. **Split** — total (default 25) over: customer one-off, customer recurring setup, MIT recurring, MIT unscheduled, pay to card, pay to bank, declined, disputes. Each row explains itself; the meter shows what is left to assign; changing the total rescales the split.
3. **Details** — amount/payout ranges, currencies, card brands, which decline codes may appear (random pick), which dispute outcomes, follow-up mix for the one-off payments (stay authorized / voided / captured later / fully refunded / partly refunded), pace, reference prefix, API-log verbosity.
4. **Generate sample data** → a confirmation ("I will create … press Continue") → live progress, Stop, per-row result, JSON/CSV report, "Check disputes now".

## Backend (`/testdata/*`, one allowlisted call per request)
`GET /config`, `POST /seal`, `POST /call {op, params, profile, idempotencyKey}`. Ops: `payment`, `capture`, `void`, `refund`, `token` (public key), `payout_card`, `payout_bank`, `dispute_lookup`. Strict validators per field (ids, amounts, PAN, references, IBAN…); prefix cannot redirect the host; `Object.prototype` names are not operations; the request echoed back has the card masked; every payment gets a `Cko-Idempotency-Key`. Responses are always an envelope `{upstream_status, data, …}` (validation errors are HTTP 400/401/403).
No new env vars (uses `CONFIG_SEAL_KEY`); `/testdata` + `/testdata/{proxy+}` are created by `/release` (api:sync).

## Brands that are not enabled (run-time behaviour)
The API refuses a brand that is not enabled for the account with **HTTP 422 `processing_error` / `<brand>_scheme_not_configured`** (seen for Discover, Diners, UnionPay on the demo account) — an API error, not a decline. The runner drops that brand for the rest of the batch and re-sends the same transaction with a working brand (declines and disputes pick a decline card / dispute row of a working brand; merchant-initiated payments keep the setup's card). Any *other* API error is probed once with a different brand: if that works the first brand is dropped, if every brand fails the same way (e.g. a wrong processing channel) nothing is dropped and the rows fail with the API reason. A brand that is enabled but **declines** is never skipped — those rows are flagged "unexpected". If every ticked brand is refused the payments fail with "No usable card brand left". The banner, the row notes and the summary ("Skipped (not enabled for this account)", "By brand") say what happened.

## Verified against the demo sandbox account (2026-11-12) — do not "improve" these without re-testing
- **On the demo account every customer-present Visa payment declines `43102` (Risk decline – Visa AFT mandate)**, masking the documented codes of the Visa decline cards; Visa MITs are approved. This is an account configuration, **not** product behaviour: the generator offers Visa like every other brand with no special-casing, and those rows simply show up as "unexpected" declines. JCB and Cartes Bancaires were approved; the JCB decline card `3528257085901927` returns `20005`.
- **The documented decline cards only decline when `processing.pan_preference: "fpan"` is sent** (the account swaps cards for network tokens, so the simulator otherwise never sees the test PAN — Mastercard decline cards were *approved*). Verified with fpan: Mastercard `20051 20005 20061 20062 20003 20057 20072 30041`, Amex `20005`, JCB `20005`, Visa `20154`. **Not** reproduced here (approved anyway): `20012 20030 20068 20182 20183 30043 30046` — left out. The Visa-documented rows are listed as "documented", unticked.
- Approved cards: Mastercard `5436031030606378` / debit `5305484748800098`, Amex `345678901234564` (cvv 1234). Recurring setup = `payment_type: Recurring` + `source.stored: true`; MIT = `merchant_initiated: true` + `previous_payment_id` (works without one too).
- Follow-ups: capture / void / refund full / partial all HTTP 202 (a refund right after a capture needs ~2.5 s — the runner waits).
- Disputes: GBP, expiry 01/2099, the magic amounts in `DISPUTE_TEST_SCENARIOS`; Mastercard and Amex rows work (no fpan needed); the dispute appeared **6–10 min** after the payment.
- Pay to card: token via `POST /tokens` with the **public** key (no Flow widget), then `/payments` with `source.type: currency_account`; **EUR only** (GBP → `processing_error`); accepted cards: Visa GB/FR/SG/US, Mastercard GB/SG (Mastercard FR → `processing_error`, US → `card_not_supported_cross_border_non_money_transfer`). Pay to bank: the IBAN goes in `destination.iban` (not `account_number`) with a full billing address; DE and FR IBANs accepted (an ES declined-IBAN returned `processing_error`). Payouts return 202 Pending — the outcome arrives by webhook.
