# Smart Dunning tab

## Session Summary (2026-11-06) — Smart Dunning (retry schedule testing)

**Where**: own nav item 🔁 in the **Manage** group (next to Payments). Not under Standalone: Smart Dunning needs a direct Checkout.com integration (docs), and Standalone is for products usable without CKO processing.

**Files**: `frontend/tabs/smart-dunning.html`, `frontend/modules/smart-dunning.js`. Backend: `/payments` now forwards `retry` (additive); `PAY_ACTION` in `standalone-routes.js` also allows `POST /payments/{pay_…}/cancellations` (cancel a retry schedule). No new API Gateway routes. Recent runs live in `localStorage['cko-dunning-runs']` (capped, see `Store.POLICIES`).

**What it does**: scenario presets (recovered on retry / retries exhausted / cancel midway / hard decline no retry / any card) → retry config (Smart Dunning toggle, `max_attempts` 1–15, `end_after_days` 1–60, downtime retries, sandbox `pan_preference: fpan`, capture) + MIT fields (`merchant_initiated: true`, `payment_type` Recurring|Unscheduled, optional `previous_payment_id`, "Create initial payment" helper using 4242… stored card) → run → live view: final-state card, per-attempt table (Authorization actions: initial MIT, Retry 1…n), merged timeline of API response + webhooks (non-consuming `/standalone/webhook-events?match=<pay_id>`) + payment actions, **Cancel retry schedule** button, polling every 3 s (stops 20 s after a final state, max 6 min). Test-card library with Load / Copy.

**Facts from the docs** (not guessed): soft-decline codes eligible for dunning: 20005 20013 20014 20015 20016 20020 20022 20030 20051 20057 20061 20065 20068 20078 20096 20098 200P1 20104 20105. Retries stop on recommendation code 03 or an ineligible code. All attempts share one `pay_` id; many Authorization actions per payment. Final status: Declined / Approved / Refunded. Sandbox simulation = `retry.dunning` + `processing.pan_preference: fpan` → **three retries, 30 s apart**; Visa `4658587554931538` ends approved, `4795395028309255` ends declined. Webhooks: `payment_retry_scheduled` (carries `retry.attempts_made/max_attempts/next_attempt_on/ends_on`), `payment_approved` / `payment_declined` (carry `retry` too). Cancel = `POST /payments/{id}/cancellations`.

**Not verified against the live sandbox yet** (check the API log on first run): the request sends `retry.enabled: true` plus `retry.dunning` (schema marks `enabled` required; the docs example omits it); whether the soft-decline cards other than the two simulation cards schedule retries in the sandbox; the hard-decline scenario outcome; the status/event name after a cancel; whether an MIT without a matching `previous_payment_id` is accepted. The workflow must subscribe to the events above (Webhooks tab → "Send events to this app") or the timeline shows API + actions only.
